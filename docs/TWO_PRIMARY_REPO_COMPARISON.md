## Decision record: Django retention vs PNLCS migration

| Decision factor | Retain Django modular monolith (selected) | Replace with PNLCS (unapproved alternative) |
| --- | --- | --- |
| Existing payment/registrar recovery | Keep Django PostgreSQL constraints, verified-capture logic and no-retry workflow | Rebuild/import customer, orders and payment evidence; test PNLCS behavior independently |
| Product feature breadth | Invoice/support/hosting tools still need development | More feature modules present in code, but operational correctness and maintenance not verified |
| Licensing / ownership | Original source and independently controlled infra remain under repo owner; repo's outbound license still needs decision | MIT allows reuse with notice; owner does **not** exclusively own upstream source; vet dependencies/licenses |
| Data migration | No cross-framework/customer DB migration | Python/PostgreSQL → PHP/MySQL, schema mapping, credentials, PII, payment/idempotency states, redirects and data integrity |
| Security and money | Existing fail-closed controls and automated Django fixtures preserved | Audit from zero, replace registrar adapter with safe HTTPS `/v1`, ensure HMAC/financial reconciliation, fund a regression sprint |
| Operational complexity | Existing Docker/PostgreSQL web+worker and GitHub Actions | Parallel PHP/Composer/npm/DB stack during transition; separate queues/process supervision and decommission plan |
| Rough engineering effort | 0 days for framework migration; focus 10–30 engineer-days on first safe sandbox milestone **subject to external access** | Feasibility spike 3–7 engineer-days; material migration likely multiple weeks to months (uncertain until PNLCS test install and schema map) |

**Recommendation:** retain Django. A migration would require a written ADR, owner approval, legal review, rollback/data migration plan, payment safety parity and a nonproduction compatibility spike. Do not run both backends as competing sources of truth.

## Reuse-first decisions / unverified evidence

- **CONFIGURE** Django security, TLS, email, PostgreSQL, CI and existing safe switches before feature expansion.
- **REUSE** Django ORM, auth, transactions and `requests` transport; do not introduce new dependencies for the targeted M5-08 fix.
- **ADAPT** patterns from PNLCS (registrar contracts, worker recovery, invoice charge attempts, domain/billing date separation) as original Python when needed.
- **BUILD** only the missing application-specific provider ownership gate and future scoped ledger/invoices, lifecycle sync and support workflows.
- Neither upstream application's full tests, dependencies, advisories or deployment paths were executed in this session; the reviewed SHA is a pin, **not** a signed security endorsement. Any copying of Openprovider WHMCS module source is blocked on licensing clarity.
